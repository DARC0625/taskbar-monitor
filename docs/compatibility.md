# 호환성 검증 계획

이 문서는 자동 검사와 실제 Windows 11 화면 검사의 범위, 통과 기준, 기록 방법을 정합니다. **검사 계획은 실행 결과가 아닙니다.** CI 성공만으로 작업표시줄 표시나 모든 Windows 11 빌드의 호환성을 보장하지 않습니다.

## 현재 확인 범위

| 구분 | 확인 수준 |
| --- | --- |
| Windows 11 x64, OS build 26200, 배율 200% | 기존 실행을 확인한 환경. 아래 수동 매트릭스 전체의 통과를 뜻하지 않음 |
| 다른 Windows 빌드·배율·모니터 구성 | 이 문서에는 실측 완료 기록 없음. 별도 실행과 결과 기록 필요 |
| Windows Server 기반 CI | 컴파일·단위 테스트·창을 만들지 않는 측정 검사와 지정 job의 패키지·설치 수명주기 검사 대상. Windows 11 GUI 호환성 결과와 분리 |

자동 검사의 구성은 **병합된 워크플로와 해당 커밋의 실제 실행 결과**를 기준으로 판단합니다. 이 문서의 통과 기준만으로 실제 검사 실행이나 성공을 대신하지 않습니다.

검증한 빌드 도구와 배포 절차는 [소스 빌드 안내](../BUILD.ko.md)를 참고하세요. 다른 링커나 Rust target으로 성공한 CI 결과를 배포 바이너리 자체의 실행 검증으로 대신하지 않습니다.

## 제품 범위와 한계

- 대상은 Windows 11 x64의 **기본 모니터에 있는 가로 작업표시줄 하나**입니다. 보조 작업표시줄에 각각 위젯을 만드는 기능은 없습니다.
- 앱은 자신의 자식 HWND를 Explorer의 `Shell_TrayWnd`에 연결합니다. DLL 주입이나 Explorer 교체를 사용하지 않지만, 이 창 구조는 공식 작업표시줄 확장 계약이 아닙니다. OS 업데이트와 다른 작업표시줄 도구의 영향을 별도로 확인해야 합니다.
- 배치는 부모 창의 client 좌표를 사용합니다. 세로·정사각형·크기가 유효하지 않은 호스트는 배치를 거절하고 연결을 기다립니다. 호스트가 숨겨졌다는 이유만으로 연결을 무효화하지 않습니다.
- 작업표시줄 안에서 폭과 위치를 제한하지만, 시작 버튼·앱 아이콘·알림 영역 사이의 빈 공간을 자동으로 예약하지는 않습니다. 겹치는 구성은 표시 항목·폭·위치를 조절해야 하며, 계산상의 경계 검사가 아이콘과의 비겹침을 증명하지 않습니다.
- 표시 항목은 1~6개, 열 폭은 88~116 DIP입니다. 설정 정규화는 모든 항목이 꺼졌을 때 CPU를 남기며, 위치 offset을 0~16000 DIP로 제한합니다. 요청 폭은 `표시 항목 수 × 열 폭 + 8 DIP`, 높이는 40 DIP이고, 실제 창은 작업표시줄 크기에 맞춰 제한됩니다.
- GPU·NPU·팬 값은 장치와 드라이버의 제공 여부에 따릅니다. `not_present`, `unsupported`, `warming_up`, `stale`, `error`를 정상 측정값 `0`으로 바꾸어 표시하지 않습니다.

구현 근거: [작업표시줄 탐색과 좌표 계산](../src/taskbar_host.rs), [연결·메뉴·복구 처리](../src/shell.rs), [설정 정규화](../src/config.rs), [렌더링](../src/render.rs).

## Windows Server CI에서 자동으로 검증할 것

PR과 기본 브랜치의 변경마다 아래 단계를 수행합니다. Windows Server 이미지별 결과는 독립적으로 남기며, runner 이미지·OS build·Rust 버전·target·커밋을 기록합니다. 워크플로가 선택한 runner에서 필요한 Windows SDK/링커가 실제 준비되어 있어야 합니다.

| 단계 | 검사 | 통과 기준 |
| --- | --- | --- |
| 형식 | `cargo fmt --all -- --check` | 변경이 필요하지 않고 종료 코드 0 |
| 단위 테스트 | `cargo test --locked --all-targets` | 모든 테스트 통과. 의존성 잠금 파일을 자동 갱신하지 않음 |
| 배포 모드 링크 | `cargo build --release --locked` | 지정 target의 release EXE 생성. 테스트 빌드 성공과 별도로 확인 |
| 수동 조작 없는 측정 | release EXE의 `--probe --seconds 6 --out <runner 임시 보고서 경로>` | 아래 JSON 판정과 종료·시간 제한 모두 충족 |
| 패키지 구성 | 지정 job에서 ZIP·설치 파일·체크섬 검사 | 필수 파일·라이선스·버전·manifest·두 배포 파일의 해시가 일치 |
| 설치 수명주기 | GitHub 호스팅 Windows runner의 지정 job에서 무인 설치·재설치·자동 시작 선택 변경·제거 | 설치 등록·바로가기·자동 시작 상태가 기대와 일치하고 기존 설정 내용이 보존됨 |
| 결과 보관 | 도구 버전, 단계 결과, 허용된 진단 요약 | 해당 커밋과 실행을 식별할 수 있고 민감한 원본 정보가 없음 |

원하는 Server runner를 사용할 수 없거나 작업이 건너뛰어진 경우는 `미실행`으로 기록합니다. 다른 runner의 성공으로 해당 항목을 채우지 않습니다. 지원하는 Rust 최소 버전은 별도 job으로 실제 확인하기 전까지 `rust-version` 선언만으로 통과했다고 판단하지 않습니다.

### probe 판정

[`--probe`](../src/diagnostics.rs)는 창을 만들지 않고 기존 시스템 상태를 읽어 보고서를 저장합니다. 보고서 출력은 쓰기 가능한 runner 폴더 안의 매번 새로운 실행 폴더에 명시적으로 지정합니다. 정상 사례는 6초를 요청하고, 각 검사 프로세스에 30초의 외부 종료 제한을 두어 종료되지 않는 경우 실패로 처리합니다. 시간 초과 정리는 그 job이 시작한 probe 프로세스에만 한정합니다. 0초 요청과 알 수 없는 인자의 거절도 별도로 확인합니다.

종료 코드 0이나 `status: completed`만 확인해서는 충분하지 않습니다. JSON을 파싱해 다음을 판정합니다.

- `schema_version == 1`, `status == completed`, `mode == passive_telemetry_probe`이고 요청한 실행 시간이 기록되어야 합니다.
- `validation.sequence_advanced`, `validation.cpu_has_valid_sample`, `validation.ram_has_valid_sample`, `validation.memory_used_not_above_total`이 모두 `true`여야 합니다.
- CPU/RAM의 백분율 범위 판정은 `true`여야 합니다. 다른 백분율 항목은 제공된 값의 판정이 `false`이면 실패하고, 표본이 없어 `null`이면 측정 불가 상태로 남깁니다.
- CPU·RAM·GPU·디스크·NPU·팬의 상태 필드가 존재하고 알려진 상태 코드여야 합니다. `ready`의 값은 유한하고 단위에 맞는 범위여야 하며, 준비되지 않은 항목의 현재 `value`는 `null`이어야 합니다. 팬 RPM과 전송률에 백분율의 상한 100을 적용하지 않습니다.
- GPU/NPU/팬이 없는 가상 runner에 특정 센서의 `ready`를 강제하지 않습니다. 선택 센서의 `error`·`stale`는 요약에 남겨 회귀 여부를 검토하되, 장치가 없다는 사실만으로 실패시키지 않습니다.
- JSON 부재·파싱 실패·비정상 종료·시간 초과·필수 CPU/RAM 표본 실패는 검사 실패입니다. 실패를 빈 보고서나 전체 `unsupported` 결과로 대체하지 않습니다.

probe는 측정값의 범위와 갱신, 상태 구분을 검사합니다. 센서의 물리적 정확도, 화면 표시 지연, 위젯 렌더러의 CPU/GPU 사용량, 장시간 안정성을 측정하는 검사가 아닙니다. 짧은 가상 서버 실행의 CPU·메모리 수치에 개인 PC용 고정 성능 합격선을 적용하지 않습니다.

CI에서는 Explorer 재시작, 디스플레이·DPI·전원 설정 변경, 위젯 창 조작, 드라이버 변경, 인위적인 하드웨어 부하를 수행하지 않습니다. 설치 수명주기 검사는 일회용 GitHub 호스팅 Windows runner에 한정하며, 로컬이나 자체 호스팅 runner에서는 실행을 거절합니다. 기존 설치·프로세스·설정 폴더·자동 시작 값·바로가기 흔적이 있으면 검사 시작 전에 중단합니다. 이 검사는 무인 설치와 자동 시작 등록·해제를 확인하지만 위젯의 실제 로그인 후 표시나 Windows 11 GUI 호환성을 검증하지는 않습니다.

## 화면 없이 검증하는 좌표 매트릭스

[`layout_rect`](../src/taskbar_host.rs)의 입력·출력만 검사합니다. 아래 배율은 Windows 설정을 바꾸는 명령이 아니라 테스트에 넣는 정수 DPI 값입니다.

| 배율 | DPI |
| --- | --- |
| 100% | 96 |
| 125% | 120 |
| 150% | 144 |
| 175% | 168 |
| 200% | 192 |
| 250% | 240 |
| 300% | 288 |

모든 배율에 대해 표시 열 수 **1~6의 각 값**, 열 폭 **88~116 DIP의 각 정수 값**을 조합합니다. 메뉴가 4 DIP씩 조절하는 경우에도 직접 읽은 설정의 중간 정수 값을 포함합니다. 테스트 정의는 링크한 소스가 기준이며, 통과 여부는 해당 커밋의 실행 결과로 확인합니다.

| 입력 종류 | 확인할 성질 |
| --- | --- |
| 일반 가로 client 영역 | 요청 폭·높이를 정수 반올림해 배치하고 수직 중앙 정렬 |
| 좁지만 유효한 가로 영역, 요청 폭보다 작은 영역 | 폭이 최소 1 pixel이고 부모 폭 이내. 오른쪽 끝을 벗어나지 않음 |
| 요청 높이보다 낮은 영역 | 높이가 부모 높이 이내이고 위아래를 벗어나지 않음 |
| offset 0·음수·오른쪽 경계 전후·매우 큰 값 | 음수는 왼쪽, 큰 값은 가능한 가장 오른쪽으로 제한 |
| 큰 client·DIP·DPI 값과 `i32::MAX`/`u32::MAX` | 중간 계산과 RECT 좌표에 정수 overflow가 없음 |
| 0·음수 크기, DPI 0, 세로·정사각형 호스트 | `None` 반환 |
| 같은 입력 반복 | 같은 RECT를 반환 |
| offset 증가 | 크기는 유지되고 left는 감소하지 않음 |
| 반올림·배율 간격 | 제한되지 않은 좌표 오차가 최대 0.5 pixel이며, 96 DIP 이동이 정확히 DPI pixel을 더함 |

유효한 결과는 `0 <= left < right <= client_width`, `0 <= top < bottom <= client_height`를 만족해야 합니다. 배율 변환은 양수에 대해 `(DIP × DPI + 48) / 96`의 정수 반올림을 기준으로 합니다. 홀수 잔여 높이는 위쪽 여백을 내림하므로 위아래 여백 차이는 최대 1 pixel입니다.

회귀 기준 예: client `3840 × 96`, DPI `192`, 요청 `584 × 40 DIP`, offset `12 DIP`의 RECT는 `(24, 8, 1192, 88)`이며 실제 크기는 `1168 × 80 pixel`입니다. 별도의 `dpi = 200` 입력은 200%와 다릅니다. 비정수 배율의 반올림 검사로 구분합니다.

이 검사는 실제 글자 잘림, 게이지 픽셀, 작업표시줄 아이콘과의 겹침, 창의 입력 처리를 검증하지 않습니다.

## 실제 Windows 11에서 수동으로 검증할 것

아래 각 항목의 초기 상태는 **실행 기록 필요**입니다. 기존 build 26200 / 200% 실행 확인을 자동으로 모든 행의 통과 표시로 복사하지 않습니다. 릴리스 후보 EXE와 그 커밋을 고정하고, 별도로 마련한 대화형 Windows 11 환경에서 검사합니다.

배율 100/125/150/175/200/250/300% 각각에서 HUD·EVA·Minimal과 밝음·어두움 표시를 확인합니다. 기본 배율에서는 표시 항목 수 1~6을 각각 확인하고, 모든 배율에서 최소한 1열/6열 및 열 폭 88/96/116 DIP의 경계 구성을 확인합니다. 전체 글꼴·폭 조합을 화면에서 확인하지 않았다면 그 범위를 결과에 남깁니다.

| 시나리오 | 조작과 관찰 | 합격 기준 |
| --- | --- | --- |
| 최초 표시·좁은 작업표시줄 | 시작·종료, 표시 항목·폭·좌우 위치 조절 | 부모 안에 표시되고 겹침은 설정으로 조절 가능. 빈 영역 예약 기능으로 오인하지 않음 |
| 글꼴·게이지 | 각 디자인에서 장치 이름, 긴 문자열, 숫자·단위·미지원 상태 관찰 | 글자·단위 겹침과 깨진 도형이 없고 필요한 말줄임이 일관됨. 색만으로 상태를 구분하지 않음 |
| 테마 | 자동 테마에서 OS 밝음/어두움 변경, 앱의 밝음/어두움 고정 | 자동 테마가 갱신되고 고정 테마는 유지. 반투명 배경 위 텍스트가 읽힘 |
| 자동 숨김 | 숨김·나타남을 반복하고 포인터를 작업표시줄 밖으로 이동 | 부모 작업표시줄의 움직임과 표시를 따르고 숨겨진 자리에 위젯만 남지 않음 |
| 전체 화면 | 일반 창·최대화·테두리 없는 전체 화면과 제공되는 전용 전체 화면 전환 | 앱이 작업표시줄의 표시 정책을 억지로 변경하거나 별도 최상위 위젯으로 남지 않음 |
| 대화상자·메뉴 | 다른 앱의 대화상자 열기, 위젯/알림 영역 우클릭, 하위 메뉴·취소·종료 | 예기치 않은 입력 포커스 이동이나 잠긴 메뉴가 없고 메뉴를 닫으면 조작·갱신이 계속됨 |
| 로그인 자동 실행 | 격리된 테스트 계정에서 메뉴로 켜기/끄기, 앱 재실행, 로그아웃·로그인, Windows 시작 앱 설정에서 사용 중지 후 확인 | 체크는 현재 EXE의 등록 상태를 반영하고 로그인 시 한 번 실행. 해제 후에는 시작되지 않음. Windows의 별도 차단은 시작 앱 설정에서 사용자가 해제 |
| 드래그·경계 | 왼쪽 끝·오른쪽 끝으로 드래그하고 여러 번 폭 변경 | 부모 영역 밖으로 이동하지 않으며 드래그 종료 후 마우스 입력을 계속 가로채지 않음 |
| 모니터 구성 | 기본 모니터 변경과 모니터 연결 구성 변경 | 현재 기본 가로 작업표시줄 하나에 다시 연결. 보조 모니터별 위젯 지원으로 기록하지 않음 |
| 실행 중 DPI 변경 | 같은 모니터 배율 변경과 서로 다른 배율의 기본 모니터 전환 | 위치·크기·문자가 새 배율에 맞게 다시 그려지고 이전 배율의 흔적이 남지 않음 |
| Explorer 재시작 | 테스트 환경에서 의도적으로 Explorer를 재시작하고 복귀 관찰 | 앱 전체가 종료되거나 Explorer가 멈추지 않고 새 작업표시줄에 다시 연결. 중복 위젯·중복 알림 아이콘이 남지 않음 |
| 절전 복귀 | 절전 후 복귀하여 시간과 센서 상태 관찰 | 수집 기준이 새로 준비되고 오래된 값을 최신 측정처럼 표시하지 않음 |
| 센서 지원 차이 | NPU/팬이 제공되지 않는 환경과 제공되는 환경을 구분 | 미지원 상태를 가짜 0으로 표시하지 않음. 제공 환경의 정확도는 별도 비교 측정으로 기록 |
| 장시간 실행 | 정해진 기간 동안 실제 위젯을 실행하고 반복 조작 | 멈춤·지속적인 자원 증가·갱신 중단 여부를 기록. 실행하지 않은 24시간 안정성을 주장하지 않음 |

Explorer·모니터·DPI·절전 변경은 수동 매트릭스의 계획이며 문서 작성이나 Server CI 과정에서 실행하지 않습니다. 드라이버 재설정이나 장치 제거를 통한 renderer 복구는 별도 테스트 환경에서만 추가 검증 항목으로 다룹니다. 수행하지 않았다면 미검증으로 남깁니다.

## 결과와 릴리스 판단

각 실행은 다음 최소 항목을 남깁니다.

| 기록 | 내용 |
| --- | --- |
| 대상 | 커밋 또는 릴리스 태그, EXE SHA-256, 빌드 target·도구 버전 |
| 환경 | Windows 종류·OS build, 배율, 기본/보조 모니터 구성, 작업표시줄 자동 숨김 여부 |
| 구성 | 디자인·테마, 표시 항목 수, 열 폭, 위치 경계 조건 |
| 결과 | 자동/수동 구분, 시나리오, 통과/실패/미실행/해당 없음, 관찰 내용 |
| 증거 | CI 실행 링크 또는 공개 가능한 화면·요약, 재현한 회귀의 이슈 링크 |

공개 기록에는 개인 PC 모델명, 사용자 이름·절대 경로, 일련번호, 앱 제목이 보이는 개인 화면, 원본 진단 JSON을 넣지 않습니다. probe 결과를 보관할 때는 상태 코드·검증 boolean·표본 수·시간 등 필요한 필드만 허용 목록으로 추려 요약합니다. `detail`, 장치 식별 정보, 전체 snapshot이나 로컬 경로를 그대로 업로드하지 않습니다.

CI 실패와 기본 수동 시나리오의 회귀는 릴리스 전에 해결하거나 영향 범위를 명시해야 합니다. 미실행 항목은 미실행으로 남깁니다. OS 업데이트나 작업표시줄·렌더러·DPI·수집 코드 변경 후에는 관련 자동 검사와 수동 행을 다시 실행하며, 이전 커밋의 성공을 새 바이너리의 결과로 표시하지 않습니다.
